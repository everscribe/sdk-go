# v0.2.0

Delivery retries for `BufferedRecorder`. Events are no longer dropped on the first failed flush. This release needs the Everscribe ingest fix that returns 503 (not 401) when an API key lookup fails for reasons other than not-found. That fix is already deployed.

## New

- `WithInitialBackoff(d)`: base wait before the first retry. Default 500ms.
- `WithMaxBackoff(d)`: cap on a single wait between retries. Default 30s.
- `WithMaxRetryDuration(d)`: how long one batch is retried before its events are dropped. Default 5m.
- `WithOnDrop(fn)`: callback for every discarded event batch, with a `DropReason` and an error: the last delivery error for `rejected` and `retries_exhausted`, the overflow error for a `buffer_full` drop from the middleware's own record, and nil otherwise. The callback must not block or call `Record`, `Flush` or `Close` on the same recorder.
- `DropReason` values: `buffer_full`, `rejected`, `retries_exhausted`, `shutdown`, `closed`.
- `Stats().Retries`: total delivery retries.
- `Stats().DroppedByReason`: events dropped, per `DropReason`.
- `event.AutoRecord`: for `Recorder` implementers, says whether the middleware will retry an event so a drop is reported once.
- `HTTPError.RetryAfter`: the server's `Retry-After`, zero if absent or invalid.

## Behavior changes

- Failed flushes are retried with jittered backoff (honoring `Retry-After`) instead of dropped. Network errors, timeouts, 429 and 5xx are retried.
- A multi-event batch rejected with 400, 409 or 413, or one that fails to encode, is split in half to isolate the bad events, up to 32 sends per batch. Events that cannot be delivered are dropped as `rejected`.
- `Stats().FlushErrs` now counts failed delivery attempts, so one flush can add several.
- `Flush` no longer returns the inner recorder's error. It returns `nil` once the events queued at the call are delivered or reported to `WithOnDrop`, or `ctx.Err()` if your context ends first. Ending the context never cancels a request. Always pass `Flush` a context with a deadline.
- `Flush` and the `Close` drain now send in batches of the flush size. v0.1.0 `Flush` sent the whole queue in one request.
- `Close` cancels in-flight work when the drain timeout elapses, reports what is left as `shutdown`, and returns `context.DeadlineExceeded`. An inner recorder that ignores context cancellation gets a 1s grace, and a late `shutdown` report can arrive after `Close` returns. `Close` can therefore take up to the drain timeout plus 1s.
- A concurrent second `Close` waits for the first to finish and returns its result.
- `WithFlushSize(n)` with `n <= 0` now keeps the default of 100, like the other options.
- `Record` after `Close`, and `PolicyBlock` waiters released by `Close`, are reported as `closed`.
- A first drop that the middleware backstop will retry no longer counts in `Dropped`; it is counted when the retry itself is dropped.
- If a handler records the request event on a different `BufferedRecorder` from the middleware's, a final drop is reported by the middleware's recorder.
